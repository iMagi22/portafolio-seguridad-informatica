01 — Resumen Ejecutivo

Se realizó una evaluación de seguridad ofensiva tipo Red Team sobre el servidor corporativo Napping 101 (IP: 192.168.56.101). El resultado fue un compromiso total del sistema, obteniendo privilegios de superusuario (root) y vulnerando completamente el modelo CIA.


La cadena de explotación partió de una vulnerabilidad Reverse Tabnabbing en el portal web, que permitió interceptar credenciales del administrador mediante una página de login falsa. Con esas credenciales se estableció acceso SSH como usuario daniel, se pivoteó a adrian inyectando código en un cron job vulnerable, y finalmente se escaló a root explotando una configuración insegura de sudo con vim NOPASSWD.

06 — Explotación: Reverse Tabnabbing

El portal de blogs acepta links externos revisados por el administrador. Al abrir el link malicioso en una nueva pestaña, el script aprovecha window.opener para redirigir silenciosamente la pestaña original a una página de login falsa controlada por el atacante.

PASO 01
📝
Envío del payload
El atacante envía la URL del payload malicioso (http://192.168.56.102:8000/payload.html) al formulario "Blog Link". El sistema lo manda al admin para revisión.
▶
PASO 02
🖱️
Admin abre el link
El administrador abre el link en una nueva pestaña. El script JavaScript se ejecuta automáticamente y detecta window.opener disponible.
▶
PASO 03
🔄
Redirección silenciosa
El script redirige la pestaña original del admin a una página de login falsa (port 8080) mientras el admin lee el payload en la nueva pestaña.
▶
PASO 04
🎯
Captura de credenciales
El admin vuelve a la pestaña "original" creyendo que su sesión expiró y re-ingresa credenciales. Netcat captura el POST en texto claro: daniel / C@ughtm3napping123

07 — Movimiento Lateral: Cron Job Hijacking

Desde la sesión de daniel, se descubrió el directorio de adrian con el script query.py que se ejecuta automáticamente cada 2 minutos vía cron job con los privilegios de adrian. El archivo tenía permisos de escritura globales — vulnerabilidad crítica.

08 — Escalada de Privilegios: vim sudo Breakout

Desde la sesión de adrian, se ejecutó sudo -l revelando una configuración insegura crítica: vim puede ejecutarse como root sin contraseña (NOPASSWD). Los editores de texto interactivos permiten abrir un shell desde su interior.

# Como adrian — Auditoría de privilegios $ export TERM=xterm $ sudo -l Matching Defaults entries for adrian on napping: env_reset, mail_badpass, secure_path=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin User adrian may run the following commands on napping: (root) NOPASSWD: /usr/bin/vim ← CRÍTICO: vim como root sin contraseña # EXPLOTACIÓN — Shell Breakout desde vim $ sudo /usr/bin/vim -c ':!/bin/sh' # vim ejecuta el comando :!/bin/sh → abre shell del proceso padre (root) # Resultado # whoami root ← ESCALADA COMPLETADA #

13 — Recomendaciones Técnicas

CRÍTICOREC-01
Mitigación Reverse Tabnabbing — rel="noopener noreferrer"
Modificar todos los hipervínculos externos en el portal. Agregar rel="noopener noreferrer" a toda etiqueta <a target="_blank">. Esto impide que la página maliciosa acceda al objeto window.opener de la pestaña original.
ALTOREC-02
Principio de Menor Privilegio — Permisos de scripts cron
Restringir permisos de escritura de query.py: chmod 644 /home/adrian/query.py. Solo el propietario legítimo (adrian) o root deben poder modificarlo. Auditar periódicamente todos los scripts ejecutados por cron jobs.
CRÍTICOREC-03
Auditoría y depuración de políticas Sudo
Eliminar inmediatamente la directiva NOPASSWD para /usr/bin/vim en /etc/sudoers. Los editores de texto interactivos permiten escape a shell. Sustituir por sudoedit con autenticación obligatoria o MFA.
ALTOREC-04
Erradicación de Hardcoded Credentials
Eliminar las credenciales MySQL de del_users.py. Implementar variables de entorno protegidas (os.environ.get('DB_PASS')) o integrar HashiCorp Vault / AWS Secrets Manager. Prohibir por política el almacenamiento de contraseñas en código fuente.
ALTOREC-05
Hardening de cookies de sesión
Configurar PHPSESSID con flags de seguridad: session.cookie_httponly = 1 y session.cookie_secure = 1 en php.ini. Agregar SameSite=Strict para prevenir ataques de sesión vía JavaScript.

15 — Conclusión y Reflexión Técnica

// CONCLUSIÓN EJECUTIVA

La evaluación Red Team sobre Napping 101 demostró un nivel de riesgo CRÍTICO. El sistema fue comprometido en su totalidad mediante una cadena de cuatro vulnerabilidades encadenadas que escalaron desde un ataque de ingeniería social web hasta el control total como root. Lo más significativo es que ninguna de las técnicas utilizadas fue avanzada: Reverse Tabnabbing, inyección en cron job, sudo misconfiguration y credenciales en texto plano son errores de configuración documentados y prevenibles con buenas prácticas básicas.

El servidor expone credenciales MySQL con sentencias destructivas en código fuente accesible por root, lo que en manos de un atacante real representaría la pérdida total de la base de datos de usuarios del portal, daño reputacional severo y posible cese de operaciones.

// REFLEXIÓN TÉCNICA — APRENDIZAJES

Este laboratorio es particularmente valioso porque demuestra que la seguridad de una aplicación web no termina en el código del servidor — el comportamiento del navegador y la gestión de pestañas también son vectores de ataque. Reverse Tabnabbing es una vulnerabilidad elegante que explota una característica legítima del navegador (window.opener) para realizar phishing dirigido sin modificar el código de la víctima.

El cron job hijacking ilustra perfectamente el principio de menor privilegio: un archivo con permisos de escritura global ejecutado automáticamente por otro usuario es una bomba de tiempo. La mitigación es trivial (chmod 644), pero el impacto de no aplicarla es devastador.

La misconfiguration de sudo con vim demuestra que delegar privilegios a herramientas interactivas es peligroso por diseño — vim, nano, less, python, perl y muchas otras herramientas permiten abrir un shell desde su interior. GTFOBins documenta cientos de binarios que pueden usarse para escape de privilegios. La regla es simple: si un binario puede ejecutar comandos arbitrarios, no debe tener sudo sin restricciones.
