01 — Objetivo

El objetivo de esta práctica fue simular el funcionamiento técnico de un atacante en el envío de correos mediante herramientas de ingeniería social, específicamente utilizando el Social-Engineer Toolkit (SET) sobre Kali Linux.


Para lograrlo se configuró un servidor Postfix como MTA local y se utilizó Gmail como relay SMTP externo autenticado mediante SASL y TLS, superando así las restricciones anti-spam que bloquean el envío directo desde IPs residenciales sin reputación.

03 — Arquitectura de la Solución

Se diseñó una cadena de envío de tres etapas para superar las restricciones de entrega directa. El envío desde una IP residencial es bloqueado por filtros anti-spam, por lo que Gmail actúa como relay externo con alta reputación.

 ¿POR QUÉ NO ENVÍO DIRECTO?
Las IPs residenciales carecen de registros SPF, DKIM y DMARC válidos. Los filtros anti-spam institucionales las bloquean automáticamente. El relay vía Gmail presta la reputación de sus servidores para que el correo sea aceptado.

05 — Configuración de Postfix

  /etc/hosts — Hostname del servidor

sudo hostnamectl set-hostname "Equipo5" sudo nano /etc/hosts 127.0.0.1 localhost 127.0.1.1 mail.equipo5.local mail ::1 localhost ip6-localhost ip6-loopback

  /etc/postfix/main.cf — Configuración principal

myhostname = Equipo5 mydomain = equipo5.local myorigin = $mydomain inet_interfaces = all inet_protocols = ipv4 mydestination = $myhostname, localhost.$mydomain, localhost, $mydomain home_mailbox = Maildir/ # ── Relay SMTP vía Gmail ────────────────────────────────────────── relayhost = [smtp.gmail.com]:587 smtp_sasl_auth_enable = yes smtp_sasl_password_maps = cdb:/etc/postfix/sasl_passwd smtp_sasl_security_options = noanonymous smtp_use_tls = yes smtp_tls_security_level = encrypt

sudo nano /etc/postfix/sasl_passwd # Contenido del archivo (16 dígitos separados cada 4): [smtp.gmail.com]:587 equipo5testingset@gmail.com:xxxx xxxx xxxx xxxx # IMPORTANTE: Kali usa Postfix con soporte CDB, NO Berkeley DB (hash) # Compilar obligatoriamente con: sudo postmap -F cdb:/etc/postfix/sasl_passwd sudo chmod 600 /etc/postfix/sasl_passwd* sudo systemctl restart postfix

11 — Análisis de Impacto (Modelo CIA)

C
Confidencialidad
IMPACTO: ALTO
Un correo de phishing convincente puede inducir al usuario a revelar credenciales institucionales. La suplantación del Dpto. de Sistemas activa confianza ciega en el receptor, aumentando la probabilidad de entrega de datos sensibles.
I
Integridad
IMPACTO: ALTO
Si el usuario hace clic en el enlace malicioso y entrega credenciales, un atacante real podría modificar datos institucionales, alterar registros académicos o comprometer cuentas con acceso a sistemas internos.
A
Disponibilidad
IMPACTO: MEDIO
Un ataque de phishing masivo podría bloquear cuentas tras múltiples intentos fallidos o ser escalado para distribuir ransomware. En este caso, el impacto en disponibilidad fue nulo al ser un entorno controlado.

12 — Recomendaciones Técnicas

CRÍTICOREC-01
Implementar SPF, DKIM y DMARC en todos los dominios institucionales
Sin estos registros, cualquier atacante puede suplantar @upslp.edu.mx desde un servidor externo. Configurar v=spf1 include:... -all y política DMARC p=reject.
CRÍTICOREC-02
Capacitación en reconocimiento de phishing para usuarios
Urgencia artificial, remitentes externos con nombres internos, URLs inesperadas. Simulacros periódicos de phishing para medir resiliencia y conciencia del personal institucional.
ALTOREC-03
Monitorear dominios typosquatting institucionales
Herramientas como dnstwist o servicios de Brand Protection para detectar dominios que imiten a upslp.edu.mx. Actuar legalmente contra registros maliciosos.
ALTOREC-04
Configurar filtros avanzados de cuarentena en Microsoft 365
El correo fue detectado como suplantación de identidad y enviado a cuarentena — señal de que los filtros funcionan. Revisión periódica de políticas Anti-Phishing y Safe Links en Microsoft Defender.
ALTOREC-05
Aplicar Zero Trust en comunicaciones institucionales
Nunca confiar en un correo solo por el nombre del remitente visible. Verificar siempre la dirección real de envío. Autenticación multifactor en todos los sistemas internos.
MEDIOREC-06
Revisar políticas de cuarentena periódicamente
Un correo de phishing capturado en cuarentena es inútil si el administrador lo libera sin revisarlo. Política de NO liberar correos de remitentes externos que suplantan identidad institucional.
MEDIOREC-07
SIEM y alertas de email security centralizado
Centralizar logs de Microsoft 365, Defender y Exchange Online. Alertas automáticas por patrones de phishing, incrementos de correos de cuarentena y logins inusuales post-entrega de correo sospechoso.

14 — Conclusión y Reflexión Técnica

// CONCLUSIÓN EJECUTIVA

La práctica demostró que el envío de correos de phishing funcional requiere una infraestructura técnica con múltiples capas: un MTA local (Postfix), credenciales SASL compiladas en formato CDB, un relay externo con reputación positiva, y un cuerpo HTML diseñado para eludir filtros de contenido.

El mensaje "SET has finished sending the emails" no garantiza entrega exitosa — la verificación real requiere revisar los logs de Postfix y el análisis de cabeceras con Google Admin Toolbox. En este caso, la cadena completa fue confirmada: SET → Postfix → Gmail → Microsoft 365 → Cuarentena → Liberado.

La diferencia entre el método Gmail relay y el dominio propio con SMTP2GO evidencia que la infraestructura de reputación DNS (SPF/DKIM/DMARC) es el factor más crítico para evadir o ser detectado por filtros institucionales.

// REFLEXIÓN TÉCNICA — APRENDIZAJES

Esta práctica evidenció que la ingeniería social no requiere vulnerabilidades de software, sino el aprovechamiento de la confianza humana. El éxito del ataque simulado dependió más de la credibilidad visual del correo y la reputación del relay que de cualquier fallo técnico en el servidor objetivo.

El modelo CIA dejó de ser abstracto: un correo de phishing creíble puede comprometer las tres dimensiones en cadena — desde la obtención de credenciales hasta el acceso a sistemas críticos. La autenticación multifactor y la formación en seguridad son la primera línea de defensa real.

Dirty COW fue a los kernels lo que el phishing es a los humanos: un vector sencillo, público y efectivo que explota algo difícil de parchear. La diferencia es que el kernel se actualiza; la conciencia humana requiere educación continua.
